Call & return, one shared handoff

Structuring the register ABI, memory layouts, and shared routines that let CALL and RETURN dereference the same dispatch-table slot through the same entry mechanism — whether it lands on real code or the translator.

draft for review — register roles and layouts proposed below, flag anything that should change

02 The constraint that shapes everything below

Thumb-1's hi-register operations are exactly three: ADD, CMP, MOV (plus BX/BLX). No LDR/STR/LDM/STM encoding accepts a high register as its base — not even the multiple-register forms.

Consequence

Every touch of r8 (dispatch table) that needs to actually address memory has to detour through a low register first — MOV Rlo, r8, do the real load/store on Rlo, then MOV r8, Rlo back if it changed. Two extra instructions, paid on every crossing. r9 (runtime pointer, §01) never pays this tax at all — it's only ever moved whole, via a plain MOV, into a C function's own argument register; nothing on the asm side ever dereferences it directly.

That per-touch tax is itself the strongest argument for making dispatch-table entry a shared routine rather than inlining it at every CALL/RETURN site (§11's already-established pattern) — a fixed cost is worth amortizing precisely because it can't be designed away. The record push/pop itself no longer needs that argument on its own merits: folding call/return records onto the ordinary operand stack (§03/§04) means they move via a plain PUSH/POP, which addresses sp implicitly and was never subject to this tax in the first place — but it still rides along fused into callHelper/returnHelper, since the dispatch-table entry each one ends in still is.

It's not a blanket tax on every touch, though — only on the four load/store families. ADD/CMP/MOV take a high register directly as one operand, no detour: ADD r1,r1,r8 is one instruction, not three. Worth checking, at each hi-register touch, whether the operation actually consuming it is one of the three exceptions before reaching for the mirror.

03 The two data layouts

Both fit in one aligned word or two, chosen so indexing and packing stay cheap.

Dispatch table entry — 8 bytes, power-of-two

code_ptru32
last_usedu32

Proposed change from §9's original {state, code_ptr, size, lru_prev, lru_next}: drop state — "not resident" is just code_ptr == TRANSLATOR_ENTRY, no separate flag needed. Drop the doubly-linked LRU list too, in favor of a plain timestamp. And drop size outright, rather than just noting it's unused — nothing on this page ever reads or writes it, and the two bytes it would have cost fold straight into widening last_used to a full word instead, at no change to the entry's total size. Compaction/eviction still needs a procedure's code length from somewhere (§11), but not a stored field: compaction's own job is keeping every resident procedure's code packed back-to-back with no gaps (that's the whole point of sliding survivors together), so a second scan through the table — find whichever other resident entry has the next-closest code_ptr above this one's, or the arena's current high-water mark if none exists — gives the boundary, and the boundary minus this entry's own code_ptr is its size. Same cost class as the LRU min-scan (§08) — O(n), paid only during the already-expensive evict/compact path, not per touch.

A linked list needs 4–6 pointer writes to unlink-and-relink on every single touch; a timestamp needs one store. Eviction becomes a linear scan for the minimum last_used — more expensive per eviction, but eviction is already the rare, heavy path (a real compile), while touching is the hot path (every call and return). At a full 32 bits, freed up by dropping size, last_used doesn't realistically wrap in any embedded system's lifetime — the scan is a plain <, no wraparound-tolerant comparison idiom needed.

No exclusion needed in that scan, either — nothing is ever pinned in this design, not even the immediate caller. §8's "currently-executing procedure must never be evicted" describes a mechanism-agnostic hazard, but the concrete mechanism here (§06) always pushes the caller's return record onto the operand stack before tail-jumping toward the callee, real or not; by the time the translator ever runs (the only place eviction ever triggers), control has already left every bit of arena-resident code, and every suspended frame — the immediate caller included — is exactly as evictable as any deeper ancestor. So the loop (§08) runs over the whole table, evicting the global LRU minimum each round, until either enough room turns up or the table empties completely with the new procedure still not fitting — which, with nothing exempted, only happens when that one procedure alone is larger than the entire arena. No smarter recovery exists at that point; it's RESOURCE_ERROR (§12), full stop. Worst case that loop costs O(n²) in the resident-procedure count n — fine, given n is small on any real embedded target and this path is already the rare, expensive one.

8 bytes total lets idx → slotAddr be a single LSLS r1,r1,#3 instead of a MULS that first has to materialize the entry size into a register.

Call/return record — one word, two halves, living on the operand stack

proc_idxu16, low half
offsetu16, high half

For a CALL site, both halves are compile-time constants — the caller's own index and the byte offset just past this CALL, within the caller's own about-to-be-fully-emitted code. They pack into one 32-bit immediate at translate time, so the push never does any runtime packing.

No dedicated control stack, and no r9 mirror-dance either: this record is pushed and popped on the ordinary operand stack, the same sp everything else here shares (§06's "sp is the real C stack" point, taken all the way). PUSH/POP address sp implicitly — it isn't one of the restricted hi registers §02 is about, so there's no mirror-down/mirror-up pair to pay on every CALL/RETURN. callHelper pushes {record, Q_idx} as a pair, not the record alone — the second word is pure 8-byte AAPCS alignment padding (§06), not a second useful value, and it costs nothing extra since Q_idx is already sitting in a register callHelper needs a moment later anyway.

04 The shared handoff

Both edges reduce to the same three-parameter entry point — CALL supplies offset=0, RETURN supplies whatever it just popped. Neither the call site nor the return site ever branches on whether the target is resident; that decision lives entirely inside enterViaDispatchTable and whatever it lands on.

05 Pseudo-Thumb

Sketch, not final encoding — enough to see where the hi/lo tax from §02 actually lands.

Conceptual decomposition vs. real shape

enterViaDispatchTable and the push/pop bodies below are the three separated concerns §04's diagram is built from — the right way to explain the mechanism, one job apiece. They're not what actually ships as three independently-reachable routines, though: none of the three is ever called from anywhere but the other two, so the real implementation fuses them into exactly two call-site-facing helpers plus one inlined tail — §06. The CALL site/RETURN listings further down already reflect that fused, real shape, not this conceptual one.

enterViaDispatchTable — conceptual only, never its own callable routine

; in:  r1 = idx, r2 = offset
; out: never returns here — tail-jumps into resident code or the translator
LSLS r1, r1, #3        ; slotAddr-relative-to-base = idx * 8
ADD  r1, r1, r8         ; hi-register ADD takes r8 directly — no mirror needed (unlike LDR/STR/LDM/STM)
LDR  r3, [r1, #0]      ; r3 = code_ptr (resident target, or the translator)
BX   r3

Good thing it isn't, too: reaching this as a fixed flash routine from arena-resident, compaction-movable call sites via an ordinary relative branch would have hit exactly §06's BL hazard. §06's fusion sidesteps that along with the round-trip — not just a speed win.

per-procedure prologue stub — the first instructions of every compiled procedure

; in: r1 = slotAddr (this procedure's own), r2 = offset+1 (1 for a fresh call)
MOV  r3, r11           ; low-mirror the LRU tick — STR has no hi-accepting form, this one's unavoidable
STR  r3, [r1, #4]      ; entry.last_used = old tick — full word, at offset 4 now size is gone
ADDS r3, r3, #1         ; bump it on the low copy — plain immediate add, no extra scratch needed
MOV  r11, r3            ; publish the bumped tick
ADD  r2, r2, pc         ; r2 = (offset+1) + (address of this instruction + 4) — reading PC as a source is always well-defined; the destination is r2, never PC
BX   r2                 ; a real branch instruction — never a data-processing write to PC, §07
; … procedure body starts here

Incrementing on the low-mirrored copy rather than reaching for a hi-register add avoids needing a second scratch register to hold the literal #1 — low-register ADDS takes an immediate directly.

push / pop the call record — conceptual only, fused into callHelper/returnHelper in §06

; push — in: r1 = packed record (proc_idx | offset<<16), r2 = spare
PUSH {r1, r2}            ; onto the ordinary operand stack — sp isn't hi, no mirror (§02); r2 is pure 8-byte padding (§06), PUSH doesn't clobber it

; pop — out: r1 = proc_idx, r2 = offset
POP  {r1, r3}             ; r1 = packed record, r3 = the padding word (discarded)
LSRS r2, r1, #16           ; r2 = offset (high half)
SXTH r1, r1                 ; r1 = proc_idx, sign-extended — SXTH not UXTH: the sentinel's 0xffff must resolve to base-8, not base+524280

Dropped the standalone BX lr each would have needed as an independent leaf — neither is one in the real shape. See §06 for what actually runs.

CALL site — inside P, calling Q

MOVS/synth  r1, #REC(P_idx, K+1)   ; both halves compile-time constant — K biased by +1, see §07
MOVS        r2, #Q_idx
MOV         r3, r10                 ; low-mirror the helper vector base (§06)
LDR         r3, [r3, #0]            ; callHelper, index 0
BX          r3                       ; tail — never returns to this site
; K = byte offset of the next line, fixed the moment this is emitted

RETURN

MOV  r3, r10            ; low-mirror the helper vector base (§06)
LDR  r3, [r3, #4]       ; returnHelper, index 1
BX   r3                  ; tail — everything it needs is already on the operand stack

06 Static helper vector, not BL

Push/pop/enter (and CLZ/REVBITS, §10's own still-open question) can't be plain arena-resident routines reached by a relative BL the way a first pass at the listings assumed. Two independent reasons, either one fatal alone.

Why BL doesn't work here

RAM is the scarce resource, not flash. These routines are fixed mechanism code — nothing about them is derived from the bytecode program being translated, so putting them in the arena at all spends RAM on something that could sit in flash for free. On an MCU, that's not a rounding error.

BL's displacement is relative to the call site, not the target. Every call site that would reach these helpers lives inside compiled, arena-resident, compaction-movable procedure code. Compaction slides that code, which changes the call site's own address relative to a fixed flash target — exactly the hazard §11 already worked through for CLZ/REVBITS specifically; this just shows it applies here too, and would have applied to a standalone enterViaDispatchTable reached the same naive way.

Fix: a second, static table — link-time-fixed, flash-resident, never touched by compaction or eviction — indexed by r10 (spare until now). Each entry is a plain 4-byte function pointer with the Thumb-mode bit already set, so nothing needs synthesizing at the call site beyond the index.

0callHelper
1returnHelper
2CLZ
3REVBITS
4…reserved — extension calls

The reserved slots aren't padding. A small, stable table of host-provided functions the bytecode invokes by index is the on-device shape of the same extension point @ppl/machine's reference interpreter already has a hook for (run<E>(prog, extension?)) — not a new concept added just to fit CLZ/REVBITS in.

Why callHelper/returnHelper, not push+enter and pop+enter separately

§04/§05's three-piece decomposition (push, pop, enterViaDispatchTable) is one job apiece, which is exactly what makes it easy to reason about — but nothing ever calls any one of the three except the other two. Keeping them as three separately-reachable routines would mean every CALL makes two round trips (into push, back out, into enter) where one fused hop does the same work, and every RETURN the same. So the real implementation fuses push + enter into callHelper, pop + enter into returnHelper, and lets the translator inline its own copy of the tiny enter logic directly into its own tail rather than reach out for a fourth shared copy at all. Three physical copies of a four-instruction sequence, each folded into whatever surrounds it, instead of one shared copy paid for with an extra hop every single time.

Fusing buys one thing beyond speed: callHelper knows, at the point it computes Q's dispatch, that the offset is always 1 (a fresh call never resumes mid-procedure) — so that value is a hardwired immediate inside the helper, not something the call site has to pass in at all.

callHelper — push + enter, fused

; in: r1 = packed record (P_idx | K+1<<16), r2 = Q_idx
; out: never returns — tail-jumps into Q's resident code or the translator
PUSH {r1, r2}            ; record + Q_idx onto the ordinary operand stack — Q_idx doubles as 8-byte padding; PUSH copies, doesn't clobber, so it's still live below
LSLS r1, r2, #3          ; slotAddr-relative = Q_idx * 8 — r1 free now the record's pushed
ADD  r1, r1, r8          ; r1 = slotAddr
LDR  r3, [r1, #0]        ; r3 = code_ptr
MOVS r2, #1               ; offset+1 = 1, hardwired — see the paragraph above
BX   r3

returnHelper — pop + enter, fused

; in: nothing — everything needed is already on the operand stack
; out: never returns — tail-jumps into the caller's resident code or the translator
POP  {r1, r3}            ; r1 = packed record, r3 = callHelper's own padding word (discarded)
LSRS r2, r1, #16         ; r2 = offset+1
SXTH r1, r1               ; r1 = caller_idx, sign-extended — SXTH not UXTH: the sentinel proc_idx (0xffff, "index -1") must resolve to r8-8, not r8+524280
LSLS r1, r1, #3           ; slotAddr-relative = caller_idx * 8
ADD  r1, r1, r8           ; r1 = slotAddr
LDR  r3, [r1, #0]         ; r3 = code_ptr
BX   r3
Resolved — the control stack is gone, folded into the operand stack

An earlier draft gave the control stack its own r9-tracked region, entries pushed/popped via the mirror-dance §02 describes. Building the actual prototype (jit-armv6m/prototype) turned up a simpler shape: a call/return record is exactly the kind of thing a native C stack already carries — return addresses, spilled locals — with no dedicated second stack of its own, so there was never a real reason for this one to be different. Folding the record onto the ordinary operand stack removes the mirror-dance entirely (PUSH/POP address sp directly, no hi-register tax to pay) and frees r9 for something that actually needs a dedicated register: a runtime pointer, set once by enter_dispatch and read back out by the translator trampoline for its own call into the compiler — §01, §09.

Sizing doesn't get harder: the same worst-case call-depth figure that used to size a separate control stack (§09) now just adds onto the operand stack's own worst-case depth instead of reserving a second region beside it.

the translator's own tail — enter, inlined directly

Never reached from outside at all — the translator is one fixed body of code, not replicated at call sites, so there's nothing to amortize by sharing this with anyone. It already holds r1 (slotAddr) and r2 (offset+1) from its own entry, unchanged across however long compiling took, so re-entering after writing the fresh code_ptr is just:

LDR  r3, [r1, #0]        ; r3 = the code_ptr just written
BX   r3

Calling a static helper — e.g. CLZ, index 2

MOV  r3, r10            ; low-mirror the helper vector base — hi reg, same tax as r8/r9 (§02)
LDR  r3, [r3, #8]       ; r3 = CLZ's fixed flash address, Thumb-bit already set
BLX  r3                  ; a real call — sets lr, the helper returns via BX LR

CLZ/REVBITS return to their own call site instead of tail-jumping onward, unlike callHelper/returnHelper — so §01's lr-is-transient convention applies to them via BLX/BX LR unchanged.

Helper stack usage: sp is the real C stack, not a second one

An earlier draft called sp "never the real C stack while compiled code runs," on the theory that a helper touching its own stack would corrupt the JIT's operand stack sitting there. Wrong mental model, not a real hazard — full picture in §09, but in short: sp is genuinely shared with whatever C stack the host used to enter the JIT, not a second, walled-off region, so a helper spilling its own locals via an ordinary prologue is an unremarkable nested call, nothing more. Call/return records (§03/§04) share this exact same sp too now, not a region of their own — the same point, applied one step further.

For single-argument helpers — CLZ/REVBITS, or any future extension taking exactly one operand-stack value — r0-in/r0-out is already plain AAPCS, confirmed by docs/jit-armv6m.md §3's own reasoning for why acc is r0 in the first place ("a single-argument helper can then be reached with a bare BLX, no MOV on either side"): no shuffling needed beyond what a normal call already does.

What's left is the same shape §3 already established for CLZ/REVBITS's leaf-ness (-Wstack-usage=0 promoted to -Werror=stack-usage=), loosened from "must be exactly 0" to "must be some documented, statically-provable N": every helper — callHelper/returnHelper (0 today, register-only), CLZ/REVBITS, any future extension — needs a known worst-case stack cost, folded into the one static budget §09 derives at enter_program.

07 Resolved: no runtime address fetch, anywhere

Every offset that ever gets pushed or handed to the prologue stub is the byte distance from a procedure's own start to a point inside its own, already-emitted code — known to the translator the instant it emits that instruction, exactly like Emitter.pc in the existing prototype. Nothing here ever needs a procedure's current absolute address at runtime.

The one scenario that would need it: reconstructing (idx, offset) from lr inside a BL-reached helper, if the push were implemented by subtracting a fetched start-address from the return address instead of just passing the two values through. Since both are already static at the call site, that reconstruction buys nothing — passing them as immediates, as above, is strictly simpler and cheaper.

Also resolved

One entry point, not two. offset+1 = 1 (a fresh call) already degenerates correctly through the same prologue stub. No separate call-only entry point needed.

Corrected — the prologue stub no longer writes PC directly

An earlier draft of this page had the prologue stub as a single ADD PC,PC,r2 — a data-processing instruction with PC as its destination, reasoning that it's a different mechanism than BX's bit 0 interworking hazard (§10, emitBrTableHelper) and so ought to sidestep it. That's true as far as it goes, but it dodged the sharper question: does ARMv6-M itself treat a data-processing write to PC as cleanly as a real branch, and does that stay true on a "compatible" ARMv7-M core (Cortex-M3/4/7) that happens to run the same binary? I don't have a confident, checked answer to either half of that — and given how deep pipelines and speculative fetch have gotten on anything newer than a Cortex-M0, "reading PC is already non-trivial, writing it outside a defined branch instruction more so" is exactly the kind of claim worth taking at face value rather than arguing around.

So instead of settling whether the permissive reading is safe, the fix removes the need to answer: the prologue stub now reads PC as an ordinary source operand (via the hi-register MOV — universally defined, unchanged from ARMv4T Thumb through every ARM core since, the same idiom ADR and every PC-relative literal-pool load already rely on), adds the offset on an ordinary low-register ADDS, and reaches its target through BX — a genuine branch instruction, the one place control transfer is unambiguously specified across the whole family. Reading PC was never the question mark; only writing it outside a branch was, so this keeps every debatable step out of the design entirely rather than resolving the debate.

Cost: two instructions instead of one, paid once per procedure entry — ADD r2,r2,pc takes pc directly as its hi-register operand (§02's exception, same shape as ADD r1,r1,r8 elsewhere on this page), so there's no separate register to hold the read-out address at all; the add and the offset-fold happen in the same instruction. What would have been a third instruction is recovered for free by folding BX's own Thumb-mode bit into r2 at the source — every producer of an offset (the CALL site's K, the pushed record's own packed value) is already a compile-time constant, so storing offset+1 instead of offset costs nothing at any of those sites and removes a separate bit-set step from the stub. Same discipline as emitBrTableHelper's own clear-for-arithmetic/restore-for-branching lesson, applied a step earlier this time. Still needs confirming on real QEMU once built, same as everything else in this design.

09 Stack layout & interrupt isolation

Two corrections to §06's "sp is the real C stack" framing, found by pushing on it rather than just restating it: the operand stack's own worst case is already a known program-level figure, not something growing arbitrarily — so the only genuinely dynamic-sized thing in the whole work area, the translator's own transient bookkeeping aside, is the compiled code itself. And ARM stacks descend while code executes upward — exactly the geometry that makes sharing one region between them work at all.

The enter_program ceiling

enter_program — the ordinary C function the host calls to run a bytecode program, which doesn't return until it terminates — computes a hard ceiling for compiled code once, on entry, and never needs to check it again for ordinary code growth: codeLimit = SP(at entry) − (worst-case operand stack, inclusive of call/return records + dispatch table + worst-case helper-call stack depth). Every term on the right is a static, program- or design-level constant: operand stack from validateProgram's own totalDepth plus the worst-case call/return record depth (both driven by proc_count/max-call-depth, §2 — the record depth used to size a separate control stack, now it just folds into this same figure instead, §06's own resolved note), dispatch table from proc_count (§2 again), worst-case helper depth from whatever documented cap §06 requires of every helper (0 today for callHelper/returnHelper, CLZ/REVBITS; some bounded, known figure for any future extension). Compiled code then bump-allocates upward exactly as §02/§06 already describe, and — the improvement over the live-collision version discussed earlier in this design — never needs a runtime check against the stack side at all for ordinary compilation: the reservation already makes a collision impossible by construction. Hitting codeLimit is the same evict+compact trigger already established, just anchored to a precomputed line instead of a detected collision.

The translator's own exception

One thing doesn't fit that static picture: the translator's own Frame stack — the very first finding in this whole design pass, that no static bound on BR_TABLE/LOOP nesting depth exists anywhere in @ppl/machine — has no single program-wide worst case the way the operand stack does, since different procedures nest arbitrarily differently. Rather than a separate reservation for it — a hard constant, or a computed max, the two options considered earlier in this design — it can just be ordinary dynamic stack usage: genuine C recursion, or an explicit alloca-grown array, coexisting with the translator's own C call stack, checked live against however much of codeLimit's margin remains right now rather than a number fixed at load time. The translator is the one place in this design allowed to encroach on codeLimit itself — lowering the effective ceiling for as long as it's running — provided it tracks that encroachment and fails into RESOURCE_ERROR (§12) the moment there's no room left for both the code it still has to emit and the Frame-stack depth this particular procedure's own nesting demands. alloca doesn't check its own bound on overflow — that's undefined behavior, not a graceful failure — so the live check has to happen before growing, not after, which is exactly the discipline the translator needs for its own reasons anyway.

One more cost belongs in enter_program's static subtraction, not the translator's live check: like any C function, the translator has a fixed prologue footprint the instant it's entered, before it's had any chance to check anything itself. That fixed cost has to be folded into the worst-case helper-stack figure enter_program reserves; only the depth beyond that floor is what the translator polices live, each time it opens a new Frame or emits another byte of code.

Interrupt isolation

Checked against the actual exception-entry pseudocode in the ARMv6-M Architecture Reference Manual (ARM DDI 0419E — PushStack()/ExceptionTaken()/ExceptionReturn()), not just recalled: the hardware pushes its 8-word exception frame (R0–R3, R12, LR, return address, xPSR — 32 bytes) onto SP_process only if CONTROL.SPSEL=='1' && CurrentMode==Thread at the instant of the exception; ExceptionTaken() then unconditionally clears SPSEL to 0 on entry to Handler mode. So a second, higher-priority exception preempting an already-running handler necessarily fires with CurrentMode==Handler, which fails that condition regardless of SPSEL's value — its own dump goes to SP_main, full stop. Nested/tail-chained interrupts can never stack more than one frame onto whichever stack Thread-mode code was using.

That's the whole mechanism for keeping interrupts off the JIT's own memory: run the JIT in Thread mode on PSP (CONTROL.SPSEL=1, set via an explicit MSR PSP,… / MSR CONTROL,… / ISB sequence — the reset default is SPSEL=0/MSP, so this is a deliberate switch, not something inherited for free), and reserve MSP exclusively for Handler-mode/interrupt use, pointed at memory entirely separate from this work area. Exactly one 32-byte exception frame ever needs to be budgeted into enter_program's subtraction, regardless of interrupt priority levels or nesting depth — only the first Thread→Handler transition can ever touch PSP.

Register isolation comes for free, mostly: an interrupt handler is just an ordinary AAPCS function, and r4–r8/r10/r11 are callee-saved by convention, so the compiler's own generated prologue/epilogue for the handler already preserves whatever subset it touches — the same guarantee this design already leans on for every ordinary nested call. Worth being explicit about one exception: AAPCS designates r9 the platform register, whose saved-ness is a platform-convention choice, not the blanket guarantee r4–r8/r10/r11 get. This design uses r9 for the runtime pointer (§01), so the build needs to actually commit to treating it as callee-saved — the usual embedded convention, but a toolchain setting to pin down deliberately, not something "AAPCS" alone guarantees on its own.

Working proposal — register roles, the two data layouts, and the shared-routine split are the parts I'd treat as fairly settled; the pseudo-Thumb is illustrative, not checked against a real encoder yet. Say which parts to fold into docs/jit-armv6m.md and which need another pass.
